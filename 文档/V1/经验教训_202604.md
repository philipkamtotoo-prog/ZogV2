# 经验教训文档 - Alien TV (Zog)

本文档记录开发过程中遇到的关键问题及解决方案，供团队成员参考。

---

## 2026-02-28: Buff 系统硬编码实现

### 问题背景
LLM（大语言模型）无法精准处理"Buff 状态"、"持续回合数"等游戏机制数值，经常产生幻觉（如Buff持续时间错误、效果数值计算错误）。

### 解决方案
将所有 Buff 逻辑从 LLM Prompt 转移到 TypeScript 硬编码运算。

### 关键决策

1. **Buff 类型定义**
   - 定义 `BuffType = 'TAUNT' | 'ATK_UP' | 'DEF_UP' | 'HEAL_OVER_TIME'`
   - 使用强类型避免字符串幻觉

2. **Store 状态管理**
   - `applyBuff`: 存在同类Buff时刷新持续时间，否则新增
   - `tickBuffs`: 回合结束时减少所有Buff持续时间并清理过期Buff

3. **战斗引擎拦截**
   - TAUNT: 强制攻击嘲讽者
   - ATK_UP: 伤害 x1.5
   - DEF_UP: 伤害 x0.5
   - HEAL_OVER_TIME: 每回合回复10%最大HP

4. **AI Prompt 简化**
   - 将Buff翻译为"情绪标签"推给AI
   - ATK_UP → "系统提示：你现在感觉力量爆棚，请在发言中表现出极度的狂妄！"
   - TAUNT → "系统提示：你现在是全场公敌，请在发言中疯狂嘲讽所有人！"

### 经济系统保护
- 预审法官新增拦截规则：禁止通过文本指令修改角色基础属性
- 只有TAUNT可通过文本指令触发（可自然叙事）
- 其他Buff必须通过游戏内道具系统获取

## 2026-02-28: 预审法官 UI 解耦

### 问题背景
Pre-Trial Judge LLM 输出了包含 `questions` 和 `options` 的复杂结构，但前端渲染逻辑与LLM输出强耦合，导致：
1. LLM 容易"脑补"选项内容
2. 前端无法灵活控制选项样式

### 解决方案
- LLM 只输出 `missing_info: 'TARGET' | 'DURATION' | 'NONE'`
- 前端根据 `missing_info` 动态生成选项
- TARGET 模式：从 store 读取存活实体列表
- DURATION 模式：硬编码 [1回合, 2回合, 3回合, 永久]

### 关键修复
- **逻辑穿透Bug**: 代码在检查clarification之前就添加了god command到队列
- 修复：先检查 `needsClarification`，只有为false时才添加到队列

## 2026-02-19: 伤害计算 De-AI-fication

### 问题背景
LLM 输出的伤害数值经常不合理（如平底锅拍一下扣1000血）。

### 解决方案
- LLM 只输出 `action_multiplier` (0.0-2.0)
- TypeScript 硬编码公式：`baseAtk * multiplier * diceRoll(0.8-1.2)`
- 根据 stance（attack/defend/hide）再进行判定

---

## 开发原则总结

1. **数值逻辑硬编码**: 所有游戏机制数值计算必须用 TypeScript，避免 LLM 幻觉
2. **LLM 只负责叙事**: LLM 输出自然语言，数值由前端/后端计算
3. **经济系统保护**: 任何绕过游戏机制的路径必须被拦截
4. **类型安全**: 使用 TypeScript 严格类型定义，减少运行时错误

## 2026-04: 项目复盘 — 为什么重起炉灶

> 本节是 ZogV1 项目的整体复盘，经验教训供下一个项目直接复用。

### 教训一：大文件是技术债的第一信号

**具体问题**：
- `battleSlice.ts` — 1958 行
- `BattleScreen.tsx` — 635 行
- `BattleScreen` 同时扮演：战斗循环引擎 + 神谕指令系统 + UI 渲染 + 经济计算 + 状态订阅（20+ 个 selector）

**经验**：
- **红线**：单个文件不超过 300 行
- **红线**：UI 组件里不写业务逻辑，业务逻辑放在 `core/` 或独立 hook/store
- **红线**：单个 Zustand store 不超过 500 行

**规则**：`超过就拆，不拆就是埋雷`。

### 教训二：核心循环必须在开工前想清楚

**具体问题**：
- 战斗的"好看"点不清晰——玩家到底在看什么？角色血条？日志文字？
- 美术卡死一个月，因为没有清晰的视觉锚点

**经验**：
- **开工前必须写出 3 句话的"核心循环描述"**，让完全不懂的人能听懂
- 示例格式："玩家在客厅看 AI 吵架 → 玩家输入指令干预 → AI 对指令做出反应 → 循环"
- 美术风格指南在开工前必须完成，中途不换

### 教训三：文档多版本冲突是常态

**具体问题**：
- `PRD.md` (v2.0)、`设计文档.md` (v6.0)、`数值系统重构.md` (v5.1) 三套零食经验值互相矛盾
- PRD.md 写 10-30 G/分钟，代码实际是 40 G/分钟

**经验**：
- **规则**：每个数值只能出现在一个文档里
- **规则**：文档名带版本号（如 `数值系统_v5.md`）
- **规则**：用 CRD 格式，标明每个功能的 [已实装/未实装/部分实装]
- **规则**：每个大版本结束后写 `经验教训_YYYYMM.md`

### 教训四：Async/await 竞态条件是 Bug 大户

**具体问题**：
- 发送上帝指令后，REJECTED 判定没拦住，代码继续往下跑（穿透执行）
- 切换对局时 AI 还带有上一局的 Buff 记忆

**经验**：
- **规则**：所有 async 操作在 REJECTED 时立刻 return，不信任后续流程
- **规则**：resetBattle() 必须清空 actionQueue、logs、buffs、globalEffects、roundCount

### 教训五：LLM Prompt 的输出格式要写死

**具体问题**：
- ClarificationResult 最初字段太多（questions、options、confirmed_action），LLM 经常漏字段
- 预审法官生成的选项格式经常错误

**经验**：
- **规则**：Prompt 写死输出格式，举例说明每个字段
- **规则**：JSON 解析必须有 safeParseJSON + 正则 fallback

### 教训六：按业务领域拆分 Store，不是按页面

**具体问题**：
- 所有战斗状态塞在 battleSlice 一个文件里
- 实际上按领域分（battle/、zog/、meta/）更清晰

**经验**：
- Store 按业务领域分，每个 store 不超过 500 行
- 大组件用 Zustand `subscribeWithSelector` 或 `useShallow`，避免无限重渲染

### 教训七：未实装功能要在文档里标注

**具体问题**：
- 粉丝牌系统、演员片酬、濒死乞讨、集火嘲讽、PIXIJ 战斗画布……设计文档写了一大堆，代码里完全没实现

**经验**：
- **规则**：每个功能清单用 `[已实装]` / `[未实装]` / `[部分实装]` 标注
- 不要在未实装的功能上花太多设计精力，先把核心循环做出来
