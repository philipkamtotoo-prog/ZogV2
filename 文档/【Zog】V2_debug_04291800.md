## 1. 本轮目标

本计划用于修复当前代码构筑完成后暴露出的 debug、状态流、硬编码和逻辑断链问题。

本轮明确不做：

- 不改战斗体验节奏。
- 不改 ActorBrain / CommandGate / Reporter 的提示词内容风格。

本轮只修：

- 调试能力。
- 安全硬编码。
- LLM / prompt / provider 解耦。
- 返回客厅失灵。
- 上帝指令通过但没有注入 prompt。

- 测试覆盖缺口。

### 3.2 增加 LLM Prompt / Response 调试日志

严重级别：P0

涉及文件：

- `src/llm/clients/llmClient.ts`
- `src/llm/llmActorBrainProvider.ts`
- `src/llm/commandGateProvider.ts`
- `src/features/reports/reportGenerator.ts`
- 建议新增：`src/llm/llmDebugLogger.ts`

当前问题：

- fetch 前没有打印 prompt。
- fetch 后没有打印 response。
- 失败时没有打印完整 error body。
- ActorBrain、CommandGate、Reporter 分散调用 LLM，但没有统一 requestId。
- 浏览器端实际走 `/api/llm` 代理，console 看不到真实 provider 和 model 上下文。

修改计划：

新增统一 LLM debug logger。

建议接口：

```ts
export type LLMTraceKind = 'ActorBrain' | 'CommandGate' | 'Reporter';

export interface LLMTracePayload {
  traceId: string;
  kind: LLMTraceKind;
  provider: string;
  baseUrl: string;
  model: string;
  messages: ChatMessage[];
  requestBody: unknown;
}

export function shouldLogLLM(): boolean;
export function logLLMRequest(payload: LLMTracePayload): void;
export function logLLMResponse(traceId: string, response: unknown): void;
export function logLLMError(traceId: string, error: unknown): void;
```

浏览器开关：

```txt
localStorage.setItem('zog_llm_debug', 'verbose')
```

日志规则：

- 默认不开，避免污染普通玩家 console。
- verbose 模式打印完整 prompt 和完整 response。
- API Key 永远不打印。
- Authorization header 永远脱敏。
- 每次请求用同一个 `traceId` 串起来。
- request 日志要能看到：
  - kind
  - model
  - baseUrl
  - messages
  - max_tokens
  - temperature
- response 日志要能看到：
  - raw response
  - `choices[0].message.content`
  - usage
  - finish_reason
- error 日志要能看到：
  - HTTP status
  - error body
  - traceId

验收标准：

- 设置 `zog_llm_debug=verbose` 后，ActorBrain 每次行动都会在 console 打印 prompt 和 response。
- CommandGate 走 LLM 时会打印 prompt 和 response。
- Reporter 走 LLM 时会打印 prompt 和 response。
- 没有 API Key 时明确打印“Stub mode / no LLM request”。
- quickEvaluate 命中时明确打印“CommandGate quickEvaluate hit / no LLM request”。
- 日志里不出现 API Key。

### 3.3 修复 quickEvaluate 通过但不注入 directorBroadcast

严重级别：P0

涉及文件：

- `src/llm/prompts/commandGatePrompt.ts`
- `src/llm/commandGateProvider.ts`
- `src/core/battle/types.ts`
- `src/engine/battleEngine.ts`
- 相关测试：`src/acceptance.test.ts`

当前问题：

- `quickEvaluate('下雨了')` 返回 `ALLOW`。
- `quickEvaluate('把 TDog 打死')` 返回 `DOWNGRADE`。
- 但 quickEvaluate 不返回 `directorBroadcast`。
- `battleEngine.submitCommand()` 只有在 `result.directorBroadcast` 存在时才 push 到 `battleState.directorBroadcasts`。
- 所以 UI 显示 `READY_TO_INJECT`，但下一次 ActorBrain prompt 里没有玩家指令。

修改计划：

引入 `DirectorBroadcastDraft`，不要让 LLM Provider 负责补 runtime 字段。

建议类型：

```ts
export interface DirectorBroadcastDraft {
  text: string;
  scope: 'GLOBAL' | 'TARGETED';
  targetActorIds: string[];
  lifetime: 'NEXT_ACTION' | 'CURRENT_BEAT';
}

export interface CommandGateResult {
  decision: CommandGateDecision;
  normalizedInput: string;
  reason: string;
  directorBroadcastDraft?: DirectorBroadcastDraft;
}
```

engine 负责补全：

```ts
const broadcast: DirectorBroadcast = {
  broadcastId: createId(...),
  text: draft.text,
  scope: draft.scope,
  targetActorIds: draft.targetActorIds,
  lifetime: draft.lifetime,
  expiresAtActionIndex: state.battleState.actorActionIndex + 1,
  reactedActorIds: [],
  sourceTransactionId: transaction.transactionId,
};
```

quickEvaluate 规则：

- `ALLOW` 必须生成 `directorBroadcastDraft`。
- `DOWNGRADE` 必须生成安全降级后的 `directorBroadcastDraft`。
- `ASK` 不生成。
- `REJECT` 不生成。

注意：

- 这不是改提示词体验，而是修复“通过后没有进入 ActorBrain prompt”的逻辑断链。
- 广播文本可以先使用最保守版本，后续再调提示词。

验收标准：

- 输入“下雨了”后，`battleState.directorBroadcasts.length + 1`。
- 下一次 ActorBrain prompt 第一段包含该 broadcast 文本。
- 输入“TDog 死了”不产生 broadcast。
- 输入“把 TDog 打死”产生 DOWNGRADE broadcast，但不直接改 HP。
- CommandTransaction 状态与 broadcast 注入一致。

### 3.4 修复 Auto 并发和返回客厅失灵

严重级别：P0

涉及文件：

- `src/engine/battleEngine.ts`
- `src/features/battle/battleStore.ts`
- `src/features/battle/components/ResultsPage.tsx`
- 相关测试：新增 engine auto / dispose 测试

当前问题：

- `startAuto()` 使用 `setInterval(async () => await step())`。
- 没有 `isStepping` 锁。
- LLM 请求慢于 interval 时会并发 step。
- 旧 engine 在玩家点击“返回客厅”后仍可能完成异步 step，并通过 `onStateChange` 把 store view 又写回 `RESULTS`。
- 这很可能就是返回客厅按钮看似失灵的原因。

修改计划：

engine 增加生命周期控制：

```ts
let disposed = false;
let isStepping = false;

function dispose(): void {
  disposed = true;
  stopAutoInterval();
}
```

`step()` 开始前：

```ts
if (disposed || isStepping) return null;
isStepping = true;
try {
  ...
} finally {
  isStepping = false;
}
```

`onStateChange` 前：

```ts
if (!disposed) config.onStateChange?.(state.battleState);
```

battleStore 增加 current engine guard：

```ts
const engineId = createId(...);
onStateChange: (state) => {
  if (get().engineId !== engineId) return;
  ...
}
```

`goToLobby()`：

```ts
const { engine } = get();
engine?.dispose();
set({ view: 'LOBBY', battleState: null, engine: null, ... });
```

验收标准：

- Auto 模式下 LLM 慢时不会并发提交多个 actor action。
- 战斗结束后点击“返回客厅”不会被旧 engine 回写到 RESULTS。
- goToLobby 后旧 engine 的 onStateChange 不再影响 store。
- 反复开战斗、返回客厅、再开战斗，不会出现多个 interval。

### 3.5 修复结算账单参数传错

严重级别：P1，但需要尽早修

涉及文件：

- `src/features/battle/components/ResultsPage.tsx`
- `src/features/reports/bill.ts`
- `src/features/reports/bill.test.ts`

当前问题：

```ts
const betAmount = betSlip?.locked ? betSlip.amount : 0;
const bill = calculateEpisodeBill(battleState, finalScores, null, betAmount);
```

`calculateEpisodeBill()` 第四个参数是 `itemsUsedCount`，这里传了 `betAmount`。

后果：

- 押注 50G 会被当成使用了 50 个道具。
- bet 参数传 null，下注账单缺失。
- payout 又在 ResultsPage 外面单独加，账单成为双轨逻辑。

修改计划：

先定义结算语义：

- 下注本金在赛前已经通过 `spendGold()` 扣除。
- 结算页只发放收入，不重复扣本金。
- 战报账单可以展示“赛前押注本金”，但不能再次影响 `addGold()`。
- payout 只计算一次。

建议拆分：

```ts
calculateEpisodeBill({
  battleState,
  finalScores,
  betSlip,
  itemsUsedCount: battleState.usedItemIds.length,
  includeAlreadyPaidExpenses: true
})
```

短期最小修复：

```ts
const bill = calculateEpisodeBill(
  battleState,
  finalScores,
  betSlip?.locked ? betSlip : null,
  battleState.usedItemIds.length
);
```

然后统一 `addGold()` 来源：

- 不要 `bill.netGold + payout` 双算。
- 要么 bill 内包含 payout，要么 ResultsPage 外单算 payout。
- 推荐 bill 成为单一节目账单来源。

验收标准：

- 押注 50G 不会显示“道具使用 ×50”。
- 赢下注只发一次 payout。
- 输下注不会在结算时再扣一次本金。
- `currentBill.netGold` 和 UI 合计一致。

### 3.6 修复淘汰事件没有写入 EventLog

严重级别：P1，但影响战报、得分和表现

涉及文件：

- `src/core/battle/combatReferee.ts`
- `src/core/battle/types.ts`
- `src/engine/battleEngine.ts`
- `src/engine/battleSimulation.ts`
- `src/features/battle/display/displayMapper.ts`
- `src/core/battle/finalScore.ts`
- `src/features/reports/finalReport.ts`
- `src/acceptance.test.ts`

当前问题：

- CombatReferee 会填 `eliminatedActorIds`。
- 但 EventLog 里没有独立的 `ACTOR_ELIMINATED` 事件。
- 只要 damage > 0，事件 type 就是 `DAMAGE_DEALT`。
- `finalScore`、战报、DisplayMapper 都在等 `ACTOR_ELIMINATED`。

修改计划：

推荐把 `CommitResult` 从单 event 改成 events：

```ts
export interface CommitResult {
  newStateVersion: number;
  events: BattleEvent[];
  primaryEventId: string;
  ...
}
```

提交一次行动时：

1. 先写 action/damage event。
2. 如果有人 currentHP 归零，追加 `ACTOR_ELIMINATED` event。
3. `applyCommitResult()` 把所有 events append 到 EventLog。
4. DisplayMapper 对每个 event 生成表现项。

如果暂时不想改大结构，短期可以：

- 在 `BattleEvent` 上增加 `eliminatedActorIds` 字段。
- `finalScore` 和 report 从该字段推导。

但长期更推荐独立事件，因为战报、表现、统计都更干净。

同时修复 `finalScore` 击杀统计：

当前逻辑：

```ts
e.type === 'ACTOR_ELIMINATED' && e.targetActorId === actor.actorId
```

这其实是在统计“这个演员被杀次数”。

正确应统计：

```ts
e.type === 'ACTOR_ELIMINATED' && e.activeActorId === actor.actorId
```

验收标准：

- 有演员被打到 0 HP 时，EventLog 出现 `ACTOR_ELIMINATED`。
- DisplayLog 出现淘汰表现。
- 战报淘汰顺序不为空。
- 击杀者获得 killScore。
- 被淘汰者不会获得自己的 killScore。

## 5. P1 LLM / BYOK / Prompt 解耦

### 5.1 当前 LLM 解耦状态评估

### 5.2 Provider 解耦修改计划

涉及文件：

- `src/llm/clients/byokConfig.ts`
- `src/llm/clients/llmClient.ts`
- `vite.config.ts`
- `src/features/lounge/components/LoungePage.tsx`
- 建议新增：`src/llm/providerRegistry.ts`

目标：

BYOK 不只保存 key，而是保存完整 provider 配置。

建议结构：

```ts
export type LLMProviderId = 'deepseek' | 'openai' | 'custom';

export interface LLMConfig {
  providerId: LLMProviderId;
  apiKey: string;
  baseUrl: string;
  model: string;
  timeout: number;
  thinkingEnabled: boolean;
  debugMode: 'off' | 'summary' | 'verbose';
}
```

配置持久化：

```txt
zog_llm_config
```

而不是只存：

```txt
zog_api_key
```

浏览器代理策略：

- 开发期可以继续使用 `/api/llm`。
- 但必须知道当前 proxy target 是哪个 provider。
- 如果要支持 OpenAI 和 custom baseUrl，必须有后端代理或 Vite proxy 动态路由。
- 不能在 UI 里说支持 OpenAI，但请求仍硬打 DeepSeek proxy。

验收标准：

- UI 可以看到当前 provider、baseUrl、model。
- DeepSeek 配置可以打 DeepSeek。
- OpenAI 配置不会误打 DeepSeek proxy。
- debug log 里显示 provider 和 model。

### 5.3 Prompt 完全解耦计划

目标：

以后调提示词时，不需要碰 engine、core、UI、经济、战斗规则。

需要拆成四层：

1. `PromptContextBuilder`
2. `PromptTemplate`
3. `OutputSchema`
4. `ProviderCall`

建议目录：

```txt
src/llm/
  prompts/
    actorBrain/
      actorBrainContext.ts
      actorBrainTemplate.ts
      actorBrainSchema.ts
      actorBrainPrompt.test.ts
    commandGate/
      commandGateContext.ts
      commandGateTemplate.ts
      commandGateSchema.ts
      commandGatePrompt.test.ts
    reporter/
      reporterContext.ts
      reporterTemplate.ts
      reporterSchema.ts
      reporterPrompt.test.ts
  providerRegistry.ts
  llmDebugLogger.ts
```

规则：

- context builder 只把 BattleState 转成 prompt context。
- template 只负责文案和排列。
- schema 定义 LLM 输出必须有哪些字段。
- provider 只负责调用模型。
- validator 只验证结构和权限。
- prompt template 不允许直接 import engine。
- prompt template 不允许改 action 规则。
- actionType、字段名、DirectorBroadcast 字段属于 contract，不是随便调的文案。

可以完全解耦的内容：

- 提示词措辞。
- 角色语气。
- 示例。
- 输出前的警告语。
- 信息排序。
- 压缩/展开战场摘要。
- 是否强调导演广播。

不能“只改 prompt”完成的内容：

- 新增/改名 `actionType`。
- 新增 ActorBrain 输出字段。
- 改 CommandGate 决策枚举。
- 改 DirectorBroadcast 字段。
- 改战斗数值结算。
- 改 target 规则。
- 改道具效果。

结论：

如果按上面拆完，以后你调整提示词的绝大多数工作可以完全解耦；但只限于“不改变结构合同”的提示词调整。凡是改变 JSON 字段、枚举、规则含义的，都必须同步 schema、validator 和测试。

## 6. Opus 是否按我们的开发计划写了

总体评价：部分遵守，关键边界没有完全遵守。

| 开发计划要求 | 当前状态 | 评价 |
| --- | --- | --- |
| core / engine / llm / features 分层 | 大体有目录 | 部分达标 |
| core 不调用 LLM / UI / storage | 基本达标 | 可以保留 |

| LLM 可 debug | 没有 | 未达标 |
| 硬编码集中配置 | 没有 | 未达标 |
| 测试覆盖关键验收 | 有 acceptance | 但部分测试只测类型/注释，不测真实行为 |

Opus 写出了“能跑的骨架”，但没有严格按我们开发计划里的“可调试、可解耦、事件可信、边界清晰”来收口。现在要先补工程地基，不要急着改体验。
