通过仔细阅读《设计文档》、《数值文档》以及《架构文档》，并比对 src/engine/battleEngine.ts 中的实际实现，我梳理了目前代码中尚未实现的功能，以及对战斗状态机架构解耦情况的分析。

一、 尚未实现的功能（除美术外）
引擎目前只实现了最核心的“回合运转、调 LLM 决策、简单验证、生成展示项”骨架。以下系统目前尚未落地：

1. 战斗AI角色与表现层缺失：

Battle Showrunner（战斗导演）： 架构文档要求有一个导演来调度 Drama Beat（节目节拍）和镜头理由，作为上下文塞给 LLM。但目前 battleEngine 里的 step() 只有计算 allowedActionTypes 和 activeActor，完全**没有调用导演（ShowrunnerProvider）**获取局势和约束的代码。
War Reporter（战地记者）： 未见独立的记者模块处理节目事件包装和播报，也没有战后简报和最终战报生成的逻辑。
Zog Reaction（前景反应与误触）： 战斗中 Zog 的局势吐槽、表情反应，以及偶发的“误触遥控器”（造成节目事故）等未实现。
2. 核心经济与计费体系缺失：

上帝指令计费闭环： submitCommand 实现了调用 CommandGate，但完全没有扣费逻辑（文档要求的：根据字数扣除 G，驳回扣 30%，ASK 暂缓扣费等）。
道具库存与设备上限限制： useItem 里判断了局内 itemUsesRemaining，但并没有扣除玩家个人背包/库存里的道具，也没有去读取“设备升级（冰箱）”的等级上限。
长线资源（金币/片酬）获取： 赌博下注（生成赛前战力赔率）、战斗结束后的 MVP 与名次结算（发放 S 片酬）、抽卡重连（花费200G）以及购买“节目变异液”。
3. 客厅与长线养成系统缺失（整个外围系统）：

Zog 好感系统（送礼、挂机收益、乞讨收益）；
演员好感与永久 Prompt 注入（解锁外观、登场特效）。
二、 架构分析与功能解耦问题
从当前的 battleEngine.ts 来看，虽然做到了宏观的“队列分离（Generation / Commit / Display）”并剥离了 LLM 判断数值的权力（数值下放给 CombatReferee），但细节上的功能解耦并没有完全实现，且存在明显的前后端逻辑、异步调用混在一起的问题：

1. 道具结算严重越权（最不解耦的地方）
架构明确规定“CombatReferee 是唯一战斗裁判，BattleEngine 不直接写具体数值规则”。 但在当前的 useItem 方法中，所有道具的数值效果（比如 HEAL_SMALL 恢复 20 HP，20% 触发 "肠胃不适"；SHIELD_GRANT 加盾加嘲讽）居然用一个巨大的 switch-case 硬编码在引擎文件里。 引擎既当了排队管理员，又当了战斗裁判。正确的做法应是包装成类似 ItemAction 丢进 commitQueue，交由统一的 CombatReferee 处理。

2. 上帝指令处理绕过主干，直接篡改状态
submitCommand 预审出结果后，对于允许的情况，引擎直接将新建的 DirectorBroadcast 直接 push 进了 state.battleState.directorBroadcasts。 这种做法没有经过类似 Action 的标准事件流转，而是原地修改数据，并直接调用 config.onStateChange 触发 UI。如果以后需要增加复杂的干预逻辑或事件回溯，这种就地修改状态的方式会非常难以维护。

3. “异步执行”与“同步突变”混杂产生的竞态条件漏洞
这是最典型的前后端（表现端与业务端）混在一起带来的架构隐患：

战斗引擎的 step() 是一个异步任务。内部有一段漫长的等待：await config.actorBrainProvider.generate(...)，可能需要好几秒。
在这几秒的空隙内，玩家在前端随时可以点按钮同步调用暴露出的 useItem。
由于 useItem 是立即原地修改 state.battleState，这就破坏了架构文档中设计的“下一次安全点（beforeNextActorAction）注入”理念！
致命结果： LLM 读取 Prompt 时演员 A 只有 10HP，正在思考“绝望地求救”。但在返回结果之前，玩家用道具把 A 奶满了。然后 step() 继续往下走，将一个旧视界的“绝望求救” Action 提交给了 CombatReferee，出现了环境与行为完全脱节的 Bug。
4. 前端直接暴露驱动点
现在的 Engine 更像是一个在浏览器直接跑的肥客户端对象，既有 setInterval 自己驱动主循环，又把 useItem, submitCommand 这样的接口暴给 UI 组件直连。由于缺乏单向数据流的事务隔离锁（比如在生成期间锁定外部突变），极易造成 UI 层与业务层纠缠在一起。
